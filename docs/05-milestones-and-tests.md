# 05. Вехи и тесты

Раздел для сборщика: в каком порядке строить игру, когда веха считается готовой, чем это доказать и что показать продюсеру. Фичи с критериями — в `feature_list.json` (id вида `M2-06`), здесь — рамка вокруг них.

Как читать:
- Критерии фич в `feature_list.json` главнее пересказа здесь. Здесь — что входит в веху, какие тесты её держат и что видит продюсер.
- «Допущение» — моя оценка без замера; проверь, если упрёшься, и запиши результат в `docs/допущения.md`.
- Доказательства (скриншоты, отчёты, замеры) — в `docs/evidence/<веха>/`. Это единственная папка доказательств: на неё ссылаются `01`–`04`.

## 1. Как устроена веха

**Веха готова, когда** (каждый пункт доказан выводом в этой сессии):
1. Все фичи вехи в `feature_list.json` — `passes: true` (фича P1 из списка резки ниже — или `deferred: true`).
2. `npm run verify` выходит с кодом 0; вывод — `docs/evidence/<веха>/verify.txt`. Цепочка `verify` полная с M0 (`02`, раздел 3): каждая ступень существует и проверяет то, что уже построено. Заглушек, которые всегда зелёные, нет. Бюджет в облаке: `verify` ≤ 20 минут, `verify:full` ≤ 30. Запуск только в фоне (`run_in_background`): `npm run verify > docs/evidence/<веха>/verify.txt 2>&1; echo "EXIT=$?" >> docs/evidence/<веха>/verify.txt`; итог читай из файла, последняя строка — `EXIT=0`. На M6 так же запускается `verify:full`. Ступень дольше бюджета — запись в `progress.md`, её долгие тесты — под тег `@full` (они идут в `e2e:full`). Тест `@full`, который закрывает фичу текущей вехи (`save.spec.ts` на M3, `perf.spec.ts` на M5), прогони отдельно тем же способом: `npx playwright test <спека> --grep @full`, вывод — в папку вехи.
3. Скриншоты ключевых экранов вехи (раздел 4.4) в `docs/evidence/<веха>/`, ты открыл их и посмотрел.
4. `git push origin HEAD:main`, сборка ссылки продюсера прошла (раздел 2).
5. Запись в `progress.md`: что сделано, тесты, открытые вопросы, блок «Что проверить продюсеру» — нумерованный список: где, что нажать, что должно получиться.

**Контрольные точки продюсера** — после M1, M3 и M6: остановись после пункта 5, если стартовое сообщение не сказало иначе. После M0, M2, M4, M5 иди дальше, продюсер смотрит ссылку, когда успевает.

**Что читать на вехе.** Не читай `docs/` целиком: на каждой вехе ниже перечислены разделы. Правила и методы Яндекса — в `03` и `02`, раздел 11 (копии документации в репозитории нет).

## 2. Ссылка для продюсера

Продюсер играет промежуточные сборки на своём телефоне и ПК по постоянной ссылке, без установки чего-либо: `https://<владелец>.github.io/<репозиторий>/` (GitHub Pages из публичного репозитория). Финальные проверки с настоящим SDK — черновик Яндекс Игр (с M4).

**Как устроено** (обязательно):
- Workflow `.github/workflows/pages.yml` уже лежит в репозитории: на каждый push в `main` он ставит Node 22, делает `npm ci` и `npm run build:pages`, публикует папку `dist-pages/`. Пока в `package.json` нет скрипта `build:pages`, workflow молча пропускает публикацию. Workflow ты не правишь: облачная сессия не может пушить файлы в `.github/workflows/` (у приложения нет такого права). Нужна правка — пункт в `QUESTIONS.md`.
- `npm run build:pages` — твой скрипт. Собирает `dist-pages/`:
  - игра в режиме playtest на моке SDK (`02`, 16.1): `__DEBUG_TOOLS__` и `__STUDIO__` включены (ползунки для продюсера, фотостудия для референсов обложки без Node), `__TEST_API__` выключен;
  - мок лежит файлом `dist-pages/sdk.js`, а `index.html` подключает его относительным путём `sdk.js`: на Pages игра живёт в подпапке, и `/sdk.js` указал бы в корень домена. В релизной сборке путь остаётся `/sdk.js` (п. 1.7);
  - параметры мока работают и тут: `?mock_ad=error`, `?mock_lang=en`, `?mock_device=mobile` (`02`, 11.9);
  - Метрика не грузится, события пишутся в консоль (`06`, раздел 5);
  - в углу метка «M2 · 2026-10-15 · 1a2b3c4» (веха, дата, короткий хеш коммита). В релизной сборке метки нет (п. 1.15);
  - с M4 — папка `dist-pages/downloads/`: `index.html` со ссылками и два архива, релизный (`npm run pack`) и playtest. Отсюда продюсер берёт архив для черновика Яндекса.
- Публикация идёт только из `main`. Работаешь в своей ветке — в конце вехи `git push origin HEAD:main` (перемотка вперёд; если не перематывается — `git fetch`, `git rebase origin/main`, повтор).
- Проверка, что ссылка обновилась: `gh run list --workflow pages.yml --limit 1` → `gh run view <id>`: ссылка обновилась, если job `deploy` — success. Job `ci` — чистый клон и `npm run verify` (при ручном запуске Run workflow — `verify:full`); упал — `gh run view <id> --log-failed` или `gh run download <id> -n ci-verify -D /tmp/ci-verify` (там `docs/evidence/verify.txt` и `release/*.zip`). Статус cancelled — запуск перебит следующим push. Зелёный `ci` на коммите вехи = проверка «чистый клон»; локальный `verify` в фоне остаётся. `verify:full` в CI — `gh workflow run pages.yml --ref main`, если у сессии есть право actions:write; нет права — пункт продюсеру: Actions → pages → Run workflow. Если `gh` в сессии не отвечает, напиши в `progress.md` «публикация не проверена» и продолжай.

**Что продюсеру нужно знать** (пишешь в «Что проверить продюсеру»): ссылку, что нового с прошлой вехи, какие параметры адреса открыть (`?debug=1` для ползунков, `?mock_ad=error` и т.п.). В РФ GitHub открывается с перебоями: на телефоне может понадобиться VPN. Если на телефоне ссылка не открывается и с VPN — запасной путь с M4: на ПК скачать playtest-архив из `downloads/` и загрузить в черновик Яндекса, черновик на телефоне открывается без VPN.

**Ползунки.** На ссылке работает `?debug=1` (`02`, раздел 15). Продюсер крутит прыжок, камеру, темп лавины, жмёт «Экспорт» и присылает JSON сообщением. Ты переносишь значения в `content/avalanche/tuning.json` и `balance.json`, пишешь в `progress.md`, что поменял.

## 5. Рубрика плейтестера

Самооценка сборщика завышена, поэтому оценивает отдельный субагент с чистым контекстом: `.claude/agents/playtester.md`. Он не видит кода и ТЗ, только игру и эту рубрику.

**Как играет.** Сборка `build:e2e`, Playwright: первые 60 секунд на свежем сохранении в мобильном проекте с касаниями, затем 5 минут на ПК; кадр каждые 2 с и на каждом событии. Потом смотрит контактные листы 3×3 (не больше 20 на прогон) и журнал событий с секундами; отдельный кадр — только для худших моментов.

| # | Критерий | 1 | 3 | 5 |
|---|---|---|---|---|
| 1 | Понятно за 5 секунд, куда бежать и зачем | не ясно, что делать | ясно после подсказки | ясно без слов: число, стена, стрелка |
| 2 | Отзывчивость управления и камеры | задержка, камера в стене | работает, но вязко | мгновенно, камера не мешает |
| 3 | Сочность: отклик на каждое действие (частицы, звук, «+N», тряска) | действие без отклика | отклик есть не везде | каждое действие ощутимо |
| 4 | Цельность стиля (свет, цвет, формы, интерфейс) | разнобой | ровно, но безлико | единый яркий зимний мир |
| 5 | Первые 60 секунд по сценарию `01`, 6.2 | обрывы, ожидание | сценарий есть, темп проседает | награда каждые 10–20 с, лавина — вау |
| 6 | Честность лавины | накрыло «ни за что» | спрятаться можно, но тесно | всегда видно, куда бежать, успеваешь |
| 7 | Хочется сыграть ещё (видна цель «что дальше») | цели нет | цель есть, далеко | следующая стена, яйцо, вершина видны |

**Отчёт** — `docs/evidence/<веха>/playtest.md`: баллы, 3 худших момента со временем и кадром, 3 правки по важности.
**Порог.** На M5 и M6: средний не ниже 3,5 и ни одного пункта ниже 3. На M2 и M3 баллы справочные: пункт ниже 3 — фича в текущей вехе или запись в `progress.md`, почему нет.
**Лимит правок (M5 и M6).** На веху — не больше 2 циклов «правки по худшим пунктам → повторный плейтест», итого до 3 прогонов. Порог не взят после второго цикла — запасной порог: средний не ниже 3,0, ни одного пункта ниже 2, на M6 пункт 5 не ниже 3. Взят запасной — `passes: true`; средний, худшие пункты и что осталось — в `progress.md` и новым пунктом в `QUESTIONS.md`. Не взят и запасной — `passes` остаётся `false`, третьего цикла нет: запись туда же, веха закрывается с этой оговоркой в итоге, работа идёт дальше. Решение по качеству принимает продюсер на контрольной точке M6.

## 7. Допущения раздела
1. Сроки вех — по 1–3 дня работы облачной сессии; это оценка, а не замер.
2. Приложение Claude на GitHub не может пушить файлы в `.github/workflows/` (у токена нет права workflows, issue anthropics/claude-code 61189), поэтому workflow положен в репозиторий заранее.
3. Сессия может пушить в `main`: прокси GitHub запрещает удалять ветки и пушить теги, но не ограничивает ветки (документация cloud-environments, раздел GitHub proxy, 03.10.2026).
4. GitHub Pages по умолчанию разрешает публикацию из основной ветки; продюсер один раз включает источник «GitHub Actions» в настройках Pages.
5. `gh run list` работает через REST и отвечает в облаке; если нет — публикацию проверяет продюсер по метке на странице.
6. Порог плейтестера 3,5 подобран на глаз; поправить по итогам M2, если оценки явно расходятся с впечатлением продюсера. Лимит 2 цикла и запасной порог 3,0 (раздел 5) — защита кредита от бесконечной полировки: плейтестер ставит меньший балл при сомнении, поэтому 3,5 может не взяться и у хорошей сборки.
