# 06. Аналитика: воронка первой сессии

Раздел для сборщика и продюсера. Здесь — канонический список событий: имена, где вызываются, сколько раз, ориентиры по времени и что значит обрыв. Как устроен модуль `src/analytics/` — `docs/02-tech.md`, раздел 13; как шаги игры ложатся на воронку — `docs/01-gdd.md`, раздел 12. Если имена расходятся, прав этот файл.

## 1. Что меряем и чем
- **Консоль Яндекс Игр** — без кода: CTR иконки и обложки, доля сессий дольше 60 с, доли сессий дольше 1, 3, 5, 10, 30 минут, время на игрока, возвраты 1, 3, 7, 14 дня, рейтинг вовлечённости, доход и показы рекламы на игрока. Шагов внутри игры там нет.
- **Яндекс Метрика в игре** — цели через `reachGoal` и параметры визита через `params`. Только она показывает, на каком шаге первой минуты уходит новичок. SDK эти события сам не шлёт.
- Счётчик ставим в первую подачу: подключение после выхода — повторная модерация (страница «Яндекс Метрика» в документации Яндекс Игр, https://yandex.ru/dev/games/doc/).

## 2. Воронка первой сессии

Кратность: `player` — один раз за жизнь игрока (флаг в `SaveData`), `session` — один раз за загрузку, `always` — каждый раз. Время — от `gameReady`, после стартовой рекламы. Ориентиры — цели геймдизайна для живого игрока, не критерии сборки; критерии сборки — в разделе 7 и GDD-01.

|---|---|---|---|---|---|---|

Имена `gameReady`, `gameTutorialStart`, `gameTutorialComplete` и `params.levelComplete` — стандартные из документации Яндекса, остальные — наши.

Параметры прогресса без отдельных целей (`always`): `params({ levelComplete: 'world_N' })` на каждой горе, `params({ waveCaught: 'wN_gM' })` на каждой поимке лавиной (гора и номер ближайшей стены выше), `params({ rebirth: n })` на каждом перерождении, `params({ goldGift: 'take' | 'saved' | 'lost' })` на каждом золотом подарке (`01`, 4.9; фича M2-12): в буфере и `__TEST__.events` это события `gold_take`, `gold_saved`, `gold_lost`, в Метрику — только параметр, без `reachGoal`. Доля `saved` от `take` — тянет ли подарок из пещеры и честно ли успеть.

## 3. Реклама и покупки

Имена — стандартные из документации Яндекса (страница «События SDK» с обёртками `showRewardedWithAnalytics` и для полноэкранной рекламы): Метрика строит по ним готовые ветки отчёта `event → <имя> → placement → <место>`. Вызываются в обёртках `src/platform` вокруг `ysdk.adv.*` и `ysdk.payments.*`.

| Событие | Когда | Параметры |
|---|---|---|
| `gameRewardedRequest` | нажата кнопка «▶ Реклама» | `placement` |
| `gameRewardedOpen` | колбэк `onOpen` | `placement` |
| `gameRewardedEarned` | колбэк `onRewarded` (награда засчитана) | `placement` |
| `gameRewardedClose` | колбэк `onClose` | `placement` |
| `gameRewardedError` | `onError` или сторож 10 с без единого колбэка (`02`, 11.4–11.5) | `placement`, `reason` |
| `gameFullscreenRequest` | нажата кнопка точки показа и кулдаун прошёл | `placement` |
| `gameFullscreenOpen` | колбэк `onOpen` | `placement` |
| `gameFullscreenClose` | колбэк `onClose` | `placement`, `wasShown` (`yes` или `no`, как в доках) |
| `gameFullscreenError` | `onError` или сторож 10 с без единого колбэка (`02`, 11.4) | `placement`, `reason` |
| `ad_resume_ok` | после любого исхода рекламы герой снова управляем, звук идёт | `placement`, `type` (`rewarded`, `fullscreen`) |
| `quit_after_inter` | `visibilitychange: hidden` или `pagehide` в течение 15 с после `gameFullscreenClose` | `placement` |
| `gameOfferView`, `gamePurchaseStart`, `gamePurchaseSuccess`, `gamePurchaseError` | только при `payments.enabled: true` (`01`, 9.3) | `productId` |

Значения `placement`: за награду — `x2_stat`, `stat_now`, `skip_gate`, `x2_chest`, `egg`, `daily_x2`, `wheel` (`01`, 9.1); полноэкранная — `portal`, `rebirth`, `menu` (`01`, 9.2).
Имена из ранних черновиков не используем: `rw_click` → `gameRewardedRequest`, `rw_open` → `gameRewardedOpen`, `rw_done` → `gameRewardedEarned`, `rw_fail` → `gameRewardedError`, `inter_shown` → `gameFullscreenOpen`.

## 4. Параметры событий
Формат — как у обёртки `trackSdkEvent` из документации Яндекса (страница «События SDK»), чтобы отчёт «Параметры событий» строил ветки:

```ts
ym(counterId, 'reachGoal', name, {
  event: { [name]: eventParams },          // placement, inShelter, day, productId…
  player: { world: 1, gate: 3, tier: 0 },  // где игрок в момент события
  device: 'mobile',                        // desktop | mobile | tablet
  session: 1,                              // номер сессии игрока из SaveData
  t: 37                                    // целые секунды от gameReady
});
```

Один раз за загрузку: `ym(counterId, 'params', { game: { appId, language, pack, build }, levelAtLaunch: 'w1_g3_t0' })`.
У `gameReady` в `event` ещё параметр `flags` — набор принятых флагов удалённой конфигурации после зажима, например `{ "w1_warnSec": 10 }`; без флагов — пустой объект (`02`, 11.11). Нужен для разбора экспериментов.
`setUserID` и `userParams` в первой версии не шлём: стандартный отчёт удержания работает без них, а лишних данных об игроке меньше (допущение).

## 5. Как устроено в коде
Подробно — `02`, 13.1. Главное:
- `track(name, params?)` принимает только имена из `src/analytics/events.ts` (тип-объединение): опечатка — ошибка `typecheck`.
- Буфер в памяти на 300 событий; в `?debug=1` — последние 30 в оверлее; в e2e — `window.__TEST__.events`.
- Отправка в Метрику — внутри `try/catch` и только если `counterId > 0` и `typeof window.ym === 'function'`: ошибка аналитики не прерывает игру.
- Флаги `player` хранятся в `SaveData` и переживают F5; флаги `session` — в памяти загрузки.
- Код счётчика попадает только в релизную сборку `build` и только при `metrikaCounterId > 0` в `game.json`. В `dev`, `build:e2e`, `build:playtest` и `build:pages` счётчика нет, события пишутся в консоль через логгер: тестовые запуски не засоряют статистику.
- Пока продюсер не дал номер (`QUESTIONS.md`, Q-009), `metrikaCounterId: 0` — игра собирается и работает, отправки нет.

## 6. Что делает продюсер в Метрике
1. metrika.yandex.ru → «Добавить счётчик» на том же Яндекс ID, что и Консоль. Снять отметку «Принимать данные только с указанных адресов»: игра живёт во фрейме на домене Яндекса. Вебвизор не включать.
2. Номер счётчика — сообщением в сессию сборщика или в `QUESTIONS.md`, Q-009. Нужен до релизного архива M6.
3. Цели: «Цели» → «Добавить цель» → «JavaScript-событие», идентификатор — имя события, точное совпадение. Одна цель на каждое имя, иначе параметры не попадут в отчёт:
   - воронка (25): `load_start`, `gameReady`, `startup_ad_start`, `startup_ad_end`, `first_input`, `gameTutorialStart`, `gate_1`, `gate_2`, `shoes_1`, `gate_3`, `first_wave_survived`, `treadmill_first`, `egg_1`, `session_60s`, `gate_4`, `rewarded_shown`, `wave_real_1`, `gate_6`, `session_180s`, `daily_claim`, `gate_9`, `session_300s`, `gameTutorialComplete`, `session_600s`, `rebirth_1`;
   - техника (1): `sdk_init_slow`;
   - реклама (11): `gameRewardedRequest`, `gameRewardedOpen`, `gameRewardedEarned`, `gameRewardedClose`, `gameRewardedError`, `ad_resume_ok`, `gameFullscreenRequest`, `gameFullscreenOpen`, `gameFullscreenClose`, `gameFullscreenError`, `quit_after_inter`;
   - покупки (4, только если они включены): `gameOfferView`, `gamePurchaseStart`, `gamePurchaseSuccess`, `gamePurchaseError`;
   - итого 37 целей, с покупками 41.
4. Отчёты «Воронка»: «Отчёты» → «Создать отчёт» → «Воронка», условие шага — «Достижение JS-цели», окно 30 минут, сегмент — только новые посетители. В воронке Метрики не больше 10 шагов, и шаги засчитываются по порядку: если шаг 3 случился раньше шага 2, игрок из воронки выпадает. Поэтому отчётов три, и в каждом только шаги, порядок которых держит сама игра:
   - «Первая минута»: `load_start` → `gameReady` → `first_input` → `gameTutorialStart` → `gate_1` → `gate_2` → `gate_3` → `first_wave_survived` → `treadmill_first` → `gate_4`;
   - «Гора 1»: `gate_4` → `gate_6` → `gate_9` → `gameTutorialComplete`;
   - «Время в игре»: `session_60s` → `wave_real_1` → `session_180s` → `session_300s` → `session_600s`.

   У `shoes_1`, `egg_1`, `rewarded_shown` и `daily_claim` время плавает, их смотрим отдельными целями в отчёте «Конверсии» с тем же сегментом. Долю пойманных первой обычной лавиной — веткой `event → wave_real_1 → caught` в отчёте «Параметры событий».
5. Проверка в черновике: адрес игры с `_ym_debug=1`, в консоли браузера строки `Reach goal` с нашими целями (`03`, 7.2, пункт 9).

## 7. Критерии приёмки (фича M4-09)
1. Каждое событие из разделов 2 и 3 уходит ровно в своей точке и с указанной кратностью: e2e по `__TEST__.events` на свежем сохранении, после F5 и во второй загрузке.
2. Порядок первой минуты: `load_start` → `gameReady` → `first_input` → `gameTutorialStart` → `gate_1` → `gate_2` → `gate_3` → `first_wave_survived` → `session_60s`; `treadmill_first` и `egg_1` — после `first_wave_survived`.
3. У каждого события есть `event`, `player`, `device`, `session`, `t`; у рекламных и `rewarded_shown` — `placement`, у `wave_real_1` — `caught`.
4. В сборках кроме `build` нет кода счётчика и запросов к `mc.yandex.ru`; в `build` при `metrikaCounterId: 0` нет вызовов `ym`.
5. Подменённый `ym`, который бросает исключение, не роняет игру и не даёт ошибок в консоли.
6. Если золотой подарок в игре (M2-12 не отложена): `gold_take`, `gold_saved`, `gold_lost` в `__TEST__.events` на своих точках, в Метрику уходят только `params({ goldGift })`, вызовов `reachGoal` с этими именами нет.

## 8. После выхода (для продюсера)
- Ориентиры: доля сессий дольше 60 с — от 65%, хорошо — от 80%; возврат 1-го дня — 10–15% и выше; рейтинг вовлечённости 60+ — игра жива, 65–71 к 3–4 неделе — хорошо.
- Дни 1–3: три воронки из раздела 6 раз в день, ищем самый большой обрыв между соседними шагами; одна гипотеза — одна правка. Чтение обрывов — столбец «Обрыв значит» в разделе 2 и `01`, раздел 12.

### 8.1 Флаги первой недели (решение продюсера 04.10, Q-025, фича M4-12)
Пять рычагов, которые продюсер крутит первыми, если воронка покажет обрыв. Флаги заводятся в Консоли (удалённая конфигурация), без новой модерации архива; механика — `02`, 11.11, диапазоны — `01a`, раздел 1. Одна гипотеза — одна правка, смотрим 2–3 дня.

| # | Флаг | Стартовое значение | Диапазон | Когда трогать (какой обрыв в разделе 2) |
|---|---|---|---|---|
| 1 | `w1_warnSec` | 8 с | от честности пещер до 14 | велика доля пойманных первой обычной лавиной (`wave_real_1` → `caught`, раздел 6): игроки не успевают в пещеру — поднять |
| 2 | `w1_firstIntervalSec`, `w2_firstIntervalSec` | 30 / 12 с | 10–60 | гора 1: ранний уход до первой лавины — опустить; гора 2: обрыв сразу после портала — поднять |
| 3 | `goldGift_mult` | 10 | 3–10 | золотой подарок обесценивает монеты (кроссовки покупаются слишком быстро) — опустить |
| 4 | `interstitialCooldownSec` | 180 с | 120–600 (нижняя граница 120 — решение 04.10; SDK Яндекса сам держит минимум 60 с) | доход с полноэкранной низкий, а удержание ровное — опустить до 150–120; растёт `quit_after_inter` — поднять |
| 5 | `sneakers1_price` | 30 монет | 10–60 | обрыв до `shoes_1` (первая покупка) — опустить |

Набор принятых флагов уходит параметром `flags` события `gameReady` (раздел 4): по нему отчёты делятся на группы эксперимента.

## 9. Допущения раздела
1. Метрика успевает отправить `quit_after_inter` при скрытии страницы; проверить по отчёту после выхода.
2. Стандартные имена рекламных событий из документации Яндекса заменяют `rw_*` и `inter_shown` из ранних черновиков (`01`, `02` и `03` приведены к этим именам).
3. `gate_2` добавлен в воронку: он есть в сценарии первой минуты `01`, 6.2, а в списке `02` его не было.
4. 37 целей (41 с покупками) укладываются в лимит одного счётчика — 200 целей (справка Метрики, сверено 03.10).
5. Воронка Метрики — до 10 шагов, шаги засчитываются строго по порядку (статьи о запуске отчёта «Воронки»; в справке Метрики порядок прямо не описан, в документации Яндекс Игр окно — «время на всю последовательность»). Если на первых данных окажется, что порядок не важен, отчёты раздела 6 можно пересобрать по смыслу, не больше 10 шагов в каждом.
